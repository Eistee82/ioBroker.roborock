## Roborock adapter for ioBroker

This adapter allows you the control, get states, cleaning history and view the map of a Roborock vacuum cleaner which is set up in the Roborock app.

## Documentation

## Requirements

- Node.js >= 22.0.0
- ioBroker.admin >= 7.6.17
- ioBroker.js-controller >= 6.0.11

## Supported robots

- **S-Series:** S4, S4 Max, S5 Max, S6, S6 Pure, S6 MaxV, S7, S7 MaxV (Pro/Ultra), S7 Pro Ultra, S7 Max Ultra, S8, S8+, S8 Pro Ultra, S8 MaxV Ultra
- **Q-Series:** Q5 Pro, Q7, Q7 Max, Q7 L5, Q8 Max
- **Q Revo:** Q Revo, Q Revo Pro
- **Qrevo:** Qrevo Slim, Qrevo S, Qrevo Curve, Qrevo Curv Series, Qrevo Edge, Qrevo Edge Series, Qrevo L, Qrevo Master, Qrevo MaxV
- **Saros:** Saros 10, Saros 10R, Saros 20 / Saros 20X, Saros Z70

## Zone cleaning
This feature only works when map creation is enabled in the adapter options. Open the map from the adapter’s web UI tab in the ioBroker admin interface; no manual URL needed.

### Map creation does not work on raspberry pi
- Draw your square meant for cleaning. Roborock supports up to 4 cleaning zones at once.

### **WORK IN PROGRESS**

- (Eistee82) The robot is drawn a quarter larger, on the app's own number rather than on taste. True to scale it is 7 map cells, and that was reported as too small to make out. The robot's own app does not draw it to scale either: its size table gives the robot 8.8 cells, 44 cm for a machine of 35, right beside the dock sizes the map already uses. Following that one number fixes a second thing at the same time - the live position marker was smaller again than the map's robot it replaces, so the robot visibly shrank the moment the live channel started reporting. Both are 8.8 cells now, and the robot stays below the 10.4 cells of a base station, which is the way round it really is.
- (Eistee82) A cleaning zone is drawn on top of the map now instead of underneath parts of it. SVG has no z-index - what is drawn last covers what came before - and the zones the user draws were created before the no-go zones read off the map, so a zone drawn over a no-go area disappeared behind it. That is worse than it looks: the zone layer is the only one that is operated, its three handles sit outside the rectangle by design, and any layer painted later takes the click meant for a handle. The zones are therefore not merely moved above the no-go zones but placed above everything, and a test now asserts they are the last layer rather than trusting the reading of one line - a layer added later would otherwise end up on top of them again without anyone noticing. The one thing this costs is that a room label lying under a zone can no longer be clicked, which is the right way round: where a zone lies, the zone is what was meant.
- (Eistee82) The dock on the map is the robot app's own picture of it now, turned the way the dock really stands. Which picture is not a matter of taste but of the reported `dock_type`: zero means a plain charging dock and gets the app's one-piece graphic, anything above it means a station and gets the station body with its charging plate laid on top - exactly the two the app's control plugin picks between, and the same rule it uses to pick them. Both are drawn to scale in map cells, 52 cm of station and 24 cm of dock, so they sit right beside the robot and its trail, which are already to scale; and both are turned against the angle the map's charger block reports, snapped onto a right angle when it comes within fifteen degrees of one - a dock stands against a wall, and a reading of -93 degrees is -90 with sensor noise on it. Two things are deliberately unchanged. The pictures come from the plugin the adapter downloads per user account, so an installation that never talked to the cloud simply does not have them: the built-in symbol is drawn first every single time and only swapped once the file has been confirmed to exist, which means nobody can end up with an empty spot where the dock used to be. And a device that reports no dock type at all keeps that symbol too, because guessing would show a base station to someone who owns a charger. The B01/Q10 maps keep the symbol as well - their geometry is measured in units the app's sizes were never proven against, and an unproven scale would put a station of the wrong size on the map.
- (Eistee82) The delete handle of a zone is a white X on a red disc now, the way the robot's own app marks it - the other two handles keep the neutral disc they share. It was a waste basket on that same neutral disc, which is the icon for removing a row from a list; on the map the handle is a corner badge two dozen pixels across, and at that size a cross plus a colour reads as "remove this" without having to be recognised as a picture first. The red is not a new colour either: it is the edge the app draws a no-go zone with, so the one warning tone on the map stays one tone, and like everything else on the map it comes in a light and a dark variant and follows the map's own scheme. The X is white in both - it sits on that red, not on the map.
- (Eistee82) Cleaning zones, their handles and the marker on a picked room now follow the map instead of always assuming a dark one. They were fixed to the robot app's dark set, which was correct while the rendered map was dark whatever the admin looked like - and white on white as soon as the map could be light. The catch is that the map has its own light/dark decision: the option **Map Colour Scheme** resolved against the theme a browser reported, which with the option pinned to *Light* or *Dark* ignores the browser altogether. The tab cannot work that out, so the adapter publishes the answer in the new read-only root state `mapColorScheme` - written at startup, before any map exists, and on every change ahead of the repaint, so the overlays can never trail the picture they lie on. The colours are the app's own two sets, proven in its control plugin: a blue wash with a blue edge on a light map, a white wash with a white edge on a dark one, and the dashed focus frame with the leash of the move handle in a twenty-percent wash of the opposite of the ground. That last value also corrects a drift - the frame was drawn at forty-five percent while the comment above it already named the app's twenty. Two elements the app gives no value for are marked as ours and derived by one stated rule rather than picked per element: the disc behind a handle glyph, because the app ships ready-made artwork that its plugin package does not contain, and the pill behind a picked room's name, because the app has no such marker at all - it highlights a room with a separate transparent image of that room, which needs geometry the tab does not have. Every one of these colours now exists exactly once, in one module, and reaches the stylesheet as a custom property; they used to sit in the stylesheet *and* as inline styles in the renderer, where the inline copy silently won and a change to the stylesheet did nothing.
- (Eistee82) The robot and the dock are drawn to scale now. A map cell is 50 mm - the coordinate conversion multiplies cell indices by 50 to get millimetres - so a size in cells is a size the symbols can share with the things they stand for. They were 25 cm and 15 cm against a machine of 35 and a station of 43, which mattered because the mop trail beside them *is* to scale: a robot smaller than its own trail makes the trail look too wide.
- (Eistee82) Picking rooms now dims the rest of the map instead of marking the picks, which is what the robot's own app does and what makes a selection readable at a glance: the rooms that are not picked fade into the ground - lighter on a light map, darker on a dark one - while the picked ones keep their full colour. The two are the app's own numbers, thirty percent of the picture kept on a light map and seventy on a dark one, and they are asymmetric on purpose, because against a dark ground a small drop already eats the drawing. The adapter draws one canvas where the app stacks layers, so the fade is applied to the colours before they are painted rather than as a veil over the finished image: a veil would dim the selection along with everything else, and it would dim the cleaning path, the robot and the zones too - in the app those sit above the map image and stay fully opaque, and they do here as well. Walls fade with the rooms, since they are part of the same bitmap. What counts as picked is what the adapter already knew: the room switches under `floors.<map>.<room>`, read only for the floor the drawn map actually belongs to, because room numbers repeat across the maps of one robot and a switch on another floor would light up an arbitrary room here. While the robot is cleaning, the rooms it reports win over any selection left standing - what it is working on is what the picture has to show. Nothing selected means nothing changes: the map is then exactly the one the adapter drew before. A change to a room switch redraws the stored map after a short pause, so picking four rooms in a row costs one canvas pass and not four. Clicking a room in the tab now goes through those same switches instead of staying in the browser - previously the tab kept its picks to itself and passed them straight to the cleaning command, so the adapter never learned about them and nothing else could either. The message that carries them may do exactly one thing: switch rooms that already exist on the floor the map belongs to, each of them a writable boolean the adapter published itself. It cannot create a room, reach another floor, or write anything else.
- (Eistee82) Turned the zone resize arrows a quarter so they run along the corner they sit on instead of across it, and dropped the remove-zone button from the dock. Every zone carries its own delete handle now, and that one removes the zone it is drawn on - while the dock button always removed the one added last, which cannot say which zone it means.
- (Eistee82) The tab now follows a theme switch made while it is open, not only one made before it was loaded. The parameter the admin passes on opening is correct at that moment and stale afterwards, so the admin own background colour is consulted first instead of last - it is what the user is looking at and therefore right in both situations. A storage write or a message from the admin is taken as a hint to look again, with a second look one frame later because the admin repaints its page after it sends the message.
- (Eistee82) Found why the tab ignored the admin dark mode: the admin passes a tab its theme in the query as `react=dark`, and the framework parses that same query but keeps only `instance` and `newReact`. Looking for a parameter named `theme` - as three earlier attempts did - finds nothing, which is also why the classic HTML tabs of other adapters follow the dark mode while this one did not. Verified in the admin own source (AdminUtils.getHref). The parameter is read first now, ahead of the stored key that had gone stale on the reporting installation.
- (Eistee82) The tab follows the admin dark mode again, this time from a source that is actually current. Measured on a running installation - admin 7.0.25 with dark mode switched on - the stored key the framework resolves the theme from held "light". No amount of fixing the evaluation helps against that, so the tab now checks three sources in order: the theme the admin hands a tab in its query string, which the framework parses but drops; then the stored key, in the admin window first; and finally the admin own background colour, which cannot be out of date because it is what the user is looking at. That last step is what catches an installation where every stored value lies.
- (Eistee82) Every cleaning zone carries its own controls now: delete, resize and move, on the places the robot's own app puts them. Deleting used to be possible only through the button beside the map, which always removed the zone added last - with five zones drawn that is the wrong one four times out of five, and there was no way to say which. The arrangement is the app's and provable rather than invented: the app draws every rectangle on the map with one shared component, and a cleaning zone gets exactly three handles from it - delete on the top left corner, resize on the bottom right, and move hanging below left on a short diagonal line, each sixteen pixels outside the rectangle, which is the same distance the dashed focus frame stands off. There is no rotate handle, because the app offers one only for no-go zones, carpets and furniture, and zone cleaning takes axis-parallel rectangles anyway. Two details of the original were deliberately not copied: its handles are centred four and a half pixels off their corner by an arithmetic slip, and its hit box is square, which overlaps the rectangle by two pixels; a round hit area of the same size keeps a clearance from the corner at every size and zoom, so a click inside a zone always belongs to that zone. The handles keep their size while the map zooms - the zone must scale, since it stands for an area on the floor, and a control must not. A zone that ends up smaller on screen than one of its own icons keeps only its rectangle: the icons would then be larger than the thing they operate and, with several zones, no longer attributable to one of them; zooming in brings them back, and the zone stays draggable and removable throughout. The pictures are the tab's own icon set, because the app's artwork is not part of the plugin package it publishes - only the sizes and positions are.
- (Eistee82) The station now says whether it is washing or drying the mop. Every V1 robot reports `wash_status`, `wash_phase`, `wash_ready` and `dry_status` in each status packet, and the adapter kept them as four bare numbers that meant nothing to anyone. They are read the way the robot's own app reads them, and only that far: `wash_status` is a bit field whose low byte says a wash task is running and whose high byte says which one, `wash_ready` means the station could wash right now without the robot driving back first, and `dry_status = 1` is drying, with `rdt` as the seconds left of that run. Six derived states appear under `dockingStationStatus`, and the dock panel of the tab shows the running job on its summary line, so a wash or a drying run - both take minutes - is visible without opening the panel. What is *not* derived is stated as plainly: the low byte's own value range is enumerated in no plugin, so it stays a number; only four wash modes have a wording in Roborock's own code and every other mode keeps its number rather than borrowing a label; and `wash_phase` gets no extra state at all, because the control plugin of the test device never reads that field. A station that publishes none of this reads as "not reported", never as "not washing" - the two look the same from the tab and only one of them is harmless to claim. Drying also became a real pair of buttons: a robot that reports `dry_status` gets the start and stop commands for mop drying, which models without their own feature list were missing entirely, and while the station dries, the panel offers Stop instead of Start - the robot reports plain charging during a drying run, so the state code alone could never tell.

The tab already filtered it, but the value stayed in the state definition and so remained visible in the object tree and to every script reading it. Models that declare their own water range keep it: there 200 may well be a level of that range, and the proof covers the standard scale only.

The app lists four routes in the order 304, 300, 301, 303 and cuts that to the first two on every mode except mop-only - so without 304 the Vac & Mop tab was left with a single route. The value was in the constants table all along and simply never offered, together with the button heights in the settings panel, which now match whether a row has a picture or not.
- (Eistee82) Fixed the dark mode staying light, in the tab and on the map alike. The correction added earlier fell back to the browser colour preference whenever no stored choice was found - and then overruled the mode the framework had already resolved correctly. On a machine whose system is light while the admin is dark, that turned the page light on purpose. Since the tab also reports its mode to the adapter for the map colours, the same mistake kept the map light as well: one fault, both symptoms. The browser preference is no longer consulted, because it says nothing about the admin. A theme switch in the admin is also picked up while the tab is open instead of only after a reload.
- (Eistee82) Corrected the four room palettes. The adapter had ported the app own colouring - the degree sort, the largest room getting colour one, the greedy four-colouring - but the colour values came from a literal the app never uses, including its grey edge entries. All four palettes now hold the values the app actually paints with, verified against colorIndexMap and colorHighLightIndexMap and their dark variants.
- (Eistee82) The rendered map has a dark mode. It could not simply follow the admin before, because the map is not drawn in the browser at all - it is a PNG the adapter renders and the tab only displays, so the browser has to say what theme it shows before the adapter can paint for it. The new option **Map Colour Scheme** does that: *Light* is the picture the adapter has always produced and remains the default, so nobody who changes nothing sees anything change; *Dark* paints floor and walls in the Roborock app's own dark colours; *Follow the admin theme* takes what the tab reports through the new root state `mapTheme`, which can also be written by hand from a script. The colours are not invented - the app builds its map as an indexed PNG and picks palette entries per theme, so both sets come out of the same table in the control plugin: floor 4 light against 25 dark, walls 42 against 43, and the driven line from the app's own light and dark theme blocks. Two limits are worth stating rather than hiding: there is exactly one rendered image per robot, so "follow the admin theme" cannot serve two browsers in two themes and the one that reported last decides for everyone - which stays bounded because a tab reports only when its own theme flips, never on a timer; and the mop, backwash and pure-clean tracks stay white in both schemes, because the light values drawn here are not the app's, so swapping only the dark half would have paired a proven colour with a guessed one. Changing the setting repaints the maps already on record straight away and costs no robot a single request, since the parsed map is stored anyway. Maps of the B01/Q10 pipelines are left alone; they build their bitmap differently and already stand on a dark ground.
- (Eistee82) The rows in the cleaning settings share their width evenly and the icons are half again as large. Each row is now as wide as the widest one and its buttons split that width, so the two passes take half each instead of huddling in a corner while the five suction steps run long. That needs a minimum width on the panel: without it the panel is only as wide as its content and full-width means nothing, which is why the rows looked ragged.
- (Eistee82) Zones and picked rooms now use the colours the robot app itself uses. The app keeps two sets and picks by the ground it draws on - blue on a light one, white on a dark one - and the adapter paints its map floor dark whatever the admin theme is, so the dark set applies. Worth recording: the app uses *less* opacity than the turquoise wash that was here before and still reads better, because white against a dark blue floor separates while a tint of the floor own family does not. Piling on opacity had only made it milky. The dark mode of the admin is also read from the surrounding window now: the tab is an iframe, and one opened before the admin has stored its choice kept the light default while everything around it was dark.
- (Eistee82) The admin dark mode now reaches the whole tab. The theme variables sat on a container inside the app, which left out two things: MUI draws tooltips, menus and dialogs through a portal into the document body, outside that container, so those kept light colours in a dark admin; and the page itself had no themed background, so everything the app did not cover stayed white - a bright frame around a dark page. They are written onto the document root now, which everything inherits from, and the page and the browser scrollbars follow the mode as well. The zone rectangle also got its weight from an inline style, so raising it in the stylesheet had changed nothing; the value now sits where it is actually read.
- (Eistee82) Zones and picked rooms stand out on the map now. A zone was a 28-percent wash behind a hairline edge, which over a blue floor read as a slightly different blue; it is stronger now and its edge keeps its weight at every zoom level, since a hairline at four-times zoom is not an edge. A picked room is marked at its name rather than across its floor - the floor is a bitmap the adapter renders and this layer has no polygon to fill - so the badge has to carry the whole signal and is now opaque with a white outline instead of a faint tint.
- (Eistee82) The consumables panel lists the robot's own wear parts and the station's under separate headings, the way the robot's own app splits its supplies page. Which part belongs where is not read off the counter: the app builds that page from two sections and takes each section's artwork from its own asset namespace, `Supply.robot` and `Supply.dock`, which names the unit outright. That corrects the one part a guess gets wrong - `filter_element`, the robot's water tank filter, counts like a station part but belongs to the robot, while only the strainer is the dock's water filter. A part no list knows is placed by its counter rather than dropped, so a future firmware cannot make a consumable invisible. A device without a dock reports only robot parts and keeps the plain list it had; an empty group is never shown as a bare heading, and a counter of zero is a value, not an absent part. The filter is called "Staubfilter" rather than the app's plain "Filter", which said little next to the dock's water filter and the robot's water tank filter.

Start is the one control reached without looking, so it belongs where the hand expects it; the settings beside it are chosen deliberately and can live in a corner. The switch bars used to stretch as a wide band across the full width of the map, over the very thing they control; they are a window in the bottom left corner now, sized by their content, with the cleaning-mode tabs on top and the settings stacked underneath - each one a caption, the step it is set to, and the switch bar below it. The number of passes joins them as a switch bar of its own between water level and mop route, where the app has it, instead of being the one dropdown left among the buttons. The panel also has room to breathe: its rounding was 42 pixels rather than the 12 it was written for, because the numeric shorthand for a corner radius is a multiple of the theme's, so the first caption ("Saugkraft") ran into the round edge. The rounding is now stated in pixels and the padding is derived from it, with the rule written down as a test instead of as a look.

The separate "Clean selected rooms" button is gone - two buttons for one intent was one too many, and the plain Start next to it quietly turned into a zoned run as soon as a rectangle was on the map, which nothing said. With rooms picked *and* zones drawn the zones win, because there is one call per run and that is the choice the engine has always made; the label now tells the truth about it rather than promising the other one. Resume keeps its name in every case: it continues the run the robot is already in. "Reset view" moved up to the status strip, next to the connection channel - it changes what is shown, not what the robot does, and among Start, Stop and Dock it was the one harmless button that looked like the rest. The explanatory line under the controls is gone with them.
- (Eistee82) The map tab has the cleaning mode as a row of tabs above the switch bars, the way the robot's own app does it, and the steps below follow the mode that is picked. Mop-only offers no suction level and vacuum-only no water level, because those two modes *are* those two values: mop-only is `fan_power = 105` and vacuum-only is `water_box_mode = 200`, so a picker for them would offer to leave the mode it stands in. For the same reason the water level "Off" is gone wherever the tabs exist - "no water" is the Vacuum tab, not a level. MAX+ shows up on the vacuum-only mode alone, which is the only one the app leaves it on and the only one the robot keeps it in; on every other mode it is reset to Balanced anyway. Mop-only offers all four mop routes, the other modes the two the app allows there. Switching a tab is one call that carries all three values at once, taken from the presets the adapter publishes, so the robot never passes through a combination nobody asked for. Nothing is invented: a level a robot does not have cannot appear on any tab, a mode the robot reports but no tab stands for (Customize) highlights nothing instead of the wrong tab, and a robot the adapter published no modes for keeps exactly the view it had - one tab that switches nothing would be worse than none. The tab captions are Roborock's own, in all eleven languages.
- (Eistee82) The cleaning mode is published as its own value, `deviceStatus.clean_mode_tab`. The robot has no field for it: what the app shows as Vac & Mop, Mop, Vacuum or Customize is what suction, water level and mop route mean together, and the two values that decide it read as something else entirely on their own. `water_box_mode = 200` is not "water off while mopping", it is the vacuum-only mode, and `fan_power = 105` is not the weakest suction level, it is the mop-only mode - so three separate dropdowns showed everything except the one thing a user looks for. The derivation follows the app's own order, including that the vacuum-only mode wins over the mop-only one and both win over the per-room markers. It is read-only; the way to change the mode stays the one call that carries all three values.
- (Eistee82) The presets of `set_clean_motor_mode` are generated from that same mode logic, which corrects four of the six that were written out by hand: the Vac & Mop triple was labelled "Indv.", the entry labelled "Vac & Mop" carried `mop_mode = 301` on a mode where the robot's own app resets it to 300, "vacuum, then mop" was in fact SmartPlan's `mop_mode = 306`, and the entry labelled "Smart Plan" was the Customize triple `106 / 204 / 302`. Robots without the vacuum-only and mop-only modes get their single combined entry instead of three that do not apply to them, and SmartPlan is no longer offered at all, because whether a robot has it hangs on a firmware bit the adapter does not read yet. A model profile that brings its own presets keeps them.
- (Eistee82) Robots that have the MAX+ suction level and no model class of their own are now offered it. `fan_power = 108` is not something a robot reports being capable of - it comes from a model table compiled into Roborock's control plugin, and reading that table correctly takes three steps: the level hides inside a shared default list rather than next to each model, three models take it away again in a callback, and a dozen more inherit or copy it from another entry. A plain search for the feature name therefore finds exactly the three models that do *not* have it. 46 models are proven to have it; the 30 of them that run on the generic profile were capped at Max until now. Nothing is ever taken away: a model profile that declares 108 itself, or that maps MAX+ onto another value the way the Saros models do, is left untouched.
- (Eistee82) Suction, mop route and water level are switch bars now instead of dropdowns, the way the robot own app shows them: every step visible side by side as a picture, the one in effect standing out, and the name of that step next to the label. These settings are picked by their picture, so hiding the steps behind a click and shrinking the pictogram to 20 pixels worked against the point of having artwork at all. Showing all steps at once also makes it obvious how many a robot offers. The groups sit next to each other because the bar floats above the map and a tall block would cover what it controls; on a narrow window they wrap. An option without artwork keeps its text, a value the robot reports but the options do not contain highlights nothing rather than lighting up the first step, and clicking the active step again does nothing instead of sending an empty command.
- (Eistee82) The suction, mop route and water level icons are drawn at 32 pixels instead of 20. The artwork is 168 pixels square, so the old size was a choice rather than a limit, and at 20 pixels the pictograms were specks next to their own label - unreadable as pictures, which is the whole reason for showing them. The selector is a little wider to match, so the longest label across the eleven languages still fits beside the larger icon.
- (Eistee82) The network interface for discovery accepts an interface name such as `eth0`, not only an IP address. The admin field offers interface names for selection, but the adapter rejected them with a warning and then bound to all interfaces - the exact situation the setting exists to prevent, and it did so silently apart from one line in the log. A name is now resolved to the IPv4 address of that interface, preferring an external address over a loopback one, and both spellings Node uses for the address family are handled. If the name matches nothing, the warning now lists the interfaces that do exist instead of only stating that the entry is invalid.
- (Eistee82) Fixed a second start failure of the same kind: `import { X, type Y }` also aborts the instance, because the esbuild js-controller compiles with does not understand a type modifier inside a named import list. It is a separate `import type` statement now, and the syntax test covers this form too - it was verified to fail on the actual line before being committed.
