## Roborock adapter for ioBroker

This adapter allows you the control, get states, cleaning history and view the map of a Roborock vacuum cleaner which is set up in the Roborock app.

## Zone cleaning
This feature only works when map creation is enabled in the adapter options. Open the map from the adapter’s web UI tab in the ioBroker admin interface; no manual URL needed.

### **WORK IN PROGRESS**

- (Eistee82) **The admin tab has a real map list, and the rename is on it.** Until now the tab knew maps only as the floor dropdown in the top bar, and that dropdown could not carry a rename for two reasons that only show up on real robots. It is filled from the `common.states` of `commands.load_multi_map`, an object the adapter creates **only when `max_multi_map > 1`** - so a robot with exactly one map would have had no rename button at all - and it hides itself below two entries. Its labels are also read once, when the device is chosen, so a map renamed from the tab would have kept its old name in the dropdown until the page was reloaded. The list therefore reads a different state, and the adapter now publishes it: **`mapInventory.maps`**, one row per slot with `mapFlag`, `name`, `addTime`, `backupCount` and `lastBackupTime`. That state is written every time the adapter reads `get_multi_maps_list` - **including the read that judges a rename** - so a new name reaches the panel by itself, and the dropdown's labels are corrected from it as well. Which floors *exist* still comes from the command object, because that is what switching writes to; the list may correct a name, not invent a destination. **Switching maps stays where it was.** The selector switches, the panel manages, and one action keeps one control. The panel shows each map's name, when it was last saved and whether the robot holds a backup - the backup line reports and offers nothing, because **backing up, restoring and deleting are established and deliberately absent**: this robot keeps one backup per map, so a new one replaces the only one there is, restoring overwrites the map that is loaded, and deleting cannot be undone. The rename **disappears** rather than greys out when the adapter published no `name_multi_map` for that robot. The length check in the browser is the adapter's own function, shared rather than reimplemented, so the field stops exactly where the robot does: **below 30 of the app's bytes**, which fifteen umlauts already exceed although they are fifteen characters.
- (Eistee82) **A stored map can be renamed.** `commands.name_multi_map` takes `{"mapFlag": 0, "name": "Cellar"}` and the robot's own map list decides whether it worked. It is offered to a robot that answers `get_multi_maps_list`, which is the same question `mapInventory` is already gated on and the right one here: a robot that cannot list its maps has no slot to rename and no way to show that a rename took. **Nothing probes the method itself** - a probe that renames a map is the rename, not a test. **The payload has a trap in it and it caught two readings before this one.** The wrapper passes its argument straight to the transport, so it proves nothing; the caller one level up builds `name_multi_map([{multi_map, name, length}])` - an **array holding one object**, where a flat object looks entirely plausible. **`length` is not the number of characters.** It is the app's own byte count, and the robot echoes it back: `get_multi_maps_list` on the test device answers `"name": "Erdgeschoss", "length": 11` and `"name": "Keller", "length": 6`, which is exactly what the ported counter computes. The limit is **fewer than 30 of those bytes, strictly** - so fifteen umlauts are already too long although they are fifteen characters. The adapter's room names have a limit of 30 as well and it is a **different rule**, in characters and inclusive; the two are separate constants with a note on each, because with ASCII no test would ever tell them apart. Both refusals the app makes are made here too, before anything is sent: too long, and a name another map already carries. **The one that took the most reading is a non-decision.** The app runs map names through `escape()` when `isSpecSupported()` holds, and this adapter writes them raw - which is only correct if that predicate is false. It is: the check is `isMiApp && (a14/a15 || a19)`, and `isMiApp` is the *absence* of Roborock's own native bridge, which the Roborock app has. So the escaping is a Mi Home path, on eighteen models, and never the one this adapter talks to. Writing an escaped name on a guess would have been invisible until the first umlaut. **Success is not claimed from the answer.** `name_multi_map` has no reply of its own, and the adapter's answer check only judges `set_*` methods - so the robot's reply counts as "accepted" whatever it says. The map list is therefore read back afterwards, and only the name in it decides: the state says confirmed, or says the robot still reports the old name, or says the list could not be read and it is unknown. Reading it back is also what would surface a rename the robot silently truncated. Deleting and restoring a map stay out, unchanged and for the reasons already written down.
- (Eistee82) **Four map blocks reported a zone that was not there, and on some robots that switched off zone editing entirely.** `CUSTOM_CARPET`, `CL_FORBIDDEN_ZONES`, `SMART_DS` and `EXT_ZONES` were read with a single 16-byte read and no record count at all. That is wrong twice over, and the second way is the one with teeth. With several records only the first arrived — but with **no** records it invented one: an empty block is `length = 0`, the read went ahead anyway, and it took its sixteen bytes from whatever came next, which is the header of the following block. Measured on the test device's own map, an empty `CUSTOM_CARPET` came back as `[28, 12, 1220, 0, 5, 0, 31712, 23618]` — that is type 28, header length 12, length 1220 and count 5 of the `DS_FORBIDDEN_ZONES` block behind it, plus its first two coordinates, read as if they were the corners of a carpet. **The damage is not the wrong number, it is what one of those blocks is used for.** `CL_FORBIDDEN_ZONES` is on the list of overlays this adapter cannot rebuild, so a map carrying one has *all* zone editing refused — `save_map` replaces every zone and wall in one go and would delete it. A phantom record made that refusal fire on a map whose block is empty, and then no no-go zone, no-mop zone or virtual wall could be added, moved or deleted on that map at all, with an error naming an overlay the map does not have. It went unnoticed because the test device sends no such block; it does send an empty `SMART_DS` on every single map, and that one produced a phantom every time. All four now read their count like the zone blocks beside them always did, and every zone block gained a guard against its own block length, so a count that claims more records than the payload holds is cut off instead of reading into the next block. The guard changes nothing on any real map measured — count and payload agree on all of them. The reference map's `FORBIDDEN_ZONES`, `DS_FORBIDDEN_ZONES` and `CARPET_FORBIDDEN_ZONE` come out byte for byte as before; the one real carpet area in the second test map is now `[[…]]` rather than `[…]`, because a list of zones is what it always should have been.
- (Eistee82) **Every map cycle got 472 KiB lighter.** `map.mapData` carried the image block three times over - `pixels.floor`, `pixels.obstacle` and `pixels.segments`, one array entry per cell - beside the grid those three are computed from, which had been published for the dividing tool and costs 23 KiB. On the reference device's own map that was 472 KiB of the 543 KiB state, written on every poll while the robot cleans, and it is gone: the grid is published, and the three lists are derived where they are read. Measured end to end on that map, `mapData` falls from 543 KiB to 71 KiB. **The derivation is not an approximation** - each list is one filter on the same cell byte, and the change was accepted by parsing the real map and comparing the derived lists against the published ones cell for cell, all 30 490 floor cells, 3 468 wall cells and 30 490 segment cells, plus the finished PNGs from both forms byte for byte. Two things in this could have gone wrong quietly and are the actual work. **A stored map outlives the version that wrote it:** the theme switch and the room selection repaint from `map.mapData` read back out of the state, and a state written before this change has the lists and no grid. A reader that only derived would have blanked every stored map at the first repaint after the update - so a published list wins whenever there is one with anything in it, and that path has its own test. **Empty ones deliberately do not count**: an empty array is truthy, so treating one as "the map carries its lists" would let a `pixels` object full of empty arrays beat a raster holding a complete floor plan, and the map would come out blank with nothing anywhere to say why. The adapter never writes that shape — the parser publishes one form or the other — but `mapData` is an ioBroker state and a state can be edited by hand. **And the grid is absent by design in three cases** - a B01/Q10 map has no such block, an image block that could not be parsed has neither field, and a grid too incompressible to publish is dropped. In that last case the lists now go out in its place rather than nothing, which is new: before, dropping the grid cost the dividing tool one map, and without the swap it would have cost the picture. Where neither form is there, the map draws its path, robot and dock and leaves the floor empty instead of throwing.
- (Eistee82) The ends of a dividing line can be placed with the arrow keys - one grid cell per press, ten with Shift. That is the case the whole function exists for: a doorway is one or two cells wide, and hitting one by dragging is fiddly with a mouse and not repeatable at all. The grips are in the tab order for it, which also makes the map's one editing gesture reachable without a pointing device. **One direction in this is not obvious and is the kind of thing that ships wrong:** the map is drawn with `py = height − row`, so a *larger* row sits *higher* on screen, and "up" on the keyboard has to add rather than subtract. It is checked by converting the moved point through the map's own conversion and asserting it lands above, not by asserting the sign - and the check was confirmed by reversing the code and watching it fail.
- (Eistee82) **A room can be divided from the tab.** The last thing the map editor could not do, and the reason was never the call - it was that `split_segment` takes a *line*, and a line needs somewhere to be drawn. It is not drawn: picking a room and pressing Divide lays one across it, the way the app does, and the user moves it. Two grips at the ends, a band along the middle for sliding the whole thing. **Dashed against solid is the entire verdict** - the line as dragged is dashed and cannot be sent; once both ends have been pulled onto the room's own wall it turns solid and can. That is Roborock's design, and its own message says so literally ("adjust the dividing line until a solid line appears"), so the wording is theirs, in all eleven languages. Four things are deliberately not the app's, because a mouse is not a finger. The line is re-snapped on **every** pointer move rather than 20 ms after release - the app waits because the scan is expensive on a phone, here it is a few thousand array reads, so the solid line appears under the pointer and the hints explain something already visible instead of arriving after a click. **Dividing mode survives a division**, since anyone re-planning a flat divides several rooms in a row. The button is **hidden rather than greyed** on a map that publishes no grid, because a B01/Q10 device has nothing to draw a line on and a permanently dead button explains nothing. And the **two resulting areas are shown in m² before anything is sent**, which the app does not do at all and which is the question the user actually has - shown and not enforced, because the app has no rule about the halves and inventing one here would refuse divisions the robot accepts. **The warning stopped guessing.** The dialog in front of every division and every merge now names the rooms in the cleaning order the robot really holds, and says plainly when none is set, instead of warning about one either way; a warning that appears whether or not it applies is a warning nobody reads. The other two items are unchanged, including the one that cannot be softened: room-bound suction and water settings live on the robot, the adapter does not have them, cannot save them and cannot put them back.
- (Eistee82) **Dividing a room now refuses in the two cases the app refuses in, and one of the limits it enforced was wrong by a factor of two.** `split_segment` renumbers every segment on the map, so a call the robot rejects is not free - it is a call whose outcome nobody can predict without asking the robot afterwards, and the room-bound settings and schedules are already gone by then. The app runs two checks before it will send one, and neither of them was here. **The room limit was read wrong.** The adapter refused a division from 31 rooms on, from a report that offered three different wordings of the same sentence and no code. The app's own check, read out of the bytecode this time, is in two stages: without the firmware feature `MaxZoneOpened` it stops at **16** rooms, with it at 32. So on a robot that lacks the feature the adapter allowed almost twice what the app does, and on one that has it, it refused a division that would have worked. **A missing feature string is not a cleared bit**, and here that distinction decides whether a working function disappears: a robot that has never reported its features gets the permissive limit, because halving the limit on silence is the same mistake that once labelled a supported water level as unsupported. **The room count now comes from the map rather than from the naming.** It used to be the number of rooms `get_room_mapping` returns, which is the number of rooms that have a *name in the cloud* - a room the user never named is on the map and missing from that list. The map's own segment count is what the app tests, and it is what is tested now. **And the second check was missing entirely:** the app will not divide a room under **2 m²**, measured off the map before anything is sent. Both checks are skipped rather than guessed when the map cannot supply the figure - a `mapData` written by an older version has no cell count, and a B01/Q10 device has no such block at all; refusing on absent data would take the function away from exactly the users whose map this adapter has not learned to measure yet. **One comment is corrected in place, and it is the one that matters most:** it said the app mirrors the y axis when it builds the dividing line. It does not. The `top + height - y` in the app's own code undoes a conversion into screen space that it made two steps earlier, and the net formula is the same `y_mm = 50 * (top + row)` every other map state uses. Following the comment instead of the formula would divide the wrong half of the room, silently, with the line still looking plausible on the map.
- (Eistee82) The parsed map now says how large each room is and where it sits on the grid, and carries the grid itself. The room's cell count and its bounding box were already being computed to place the room label and were then thrown away; they are published beside the label now, so the area in m² is a multiplication rather than a second pass over the map. Both cover the room's **floor** cells, which is what the label position has always been derived from - counting the walls in would move every label. The grid is new: one byte per cell, run-length coded, about 23 KiB beside the 472 KiB of derived pixel lists that already went out, so under 5 % more. It is there because the three lists that were already published cannot answer the one question dividing a room asks - `pixels.obstacle` keeps a bare cell index and throws away which room the wall belongs to, and on the reference device 3467 of 3468 wall cells belong to one. Deliberately **not** gzipped, which would have been 4 KiB: it saves 19 KiB on a payload that is already 472 KiB, and costs an asynchronous decoder in the browser. The saving worth having is a different one and is written down where the next person will find it - publishing only the grid and deriving the three lists from it would turn 472 KiB into about 5 KiB, and that touches working drawing code.
- (Eistee82) Removed a second, broken reading of the cleaning estimate on the Saros Z70. The model class searched the answer of `app_get_clean_estimate_info` for `clean_time` and `clean_area` and published two states from them. Neither field is part of that answer: the real one nests its numbers under `clean_estimate` and calls them `total_time`, `total_area` and so on - `clean_time` and `clean_area` are field names of the status packet and the cleaning records, borrowed here by mistake. The two states were therefore never written, not once, which is why nobody noticed. Nothing is re-derived in their place, because the numbers already arrive: the shared V1 reader answers the same call and publishes eight properly named estimate states from the nested payload, so a second reading would only have put minutes beside seconds with nothing to say which to believe. Worth recording separately: the dead code had a **test**, and the test passed - it fed a hand-made payload shaped to fit the wrong field names, so the coverage looked real. That test now pins the answer the robot actually sends.
- (Eistee82) The Saros Z70 no longer shows a mop wash mode it cannot use. Reading back the dock's wash frequency, a robot **without** the "New Smart" firmware feature was shown exactly that mode whenever its interval was not a multiple of five minutes - and writing the same value back was refused, because the adapter knows the robot does not have it. Display and write path contradicted each other, and the state was not hypothetical: 21 minutes is the marker the robot's own app sends for its third interval mode. The cause was a rule ported from the wrong robot. It comes from the S7 Max Ultra's control plugin, where the number 2 means "Level"; on the Z70 the same number means "New Smart", so a rule that was a harmless display quirk in its home became a contradiction after the move. It is gone: without the feature the mode now reads as Custom, which is what the source rule effectively does - even there, "Level" has no selectable entry and could never be written back either. Nothing changed on the write path, which already accepted only 10 to 50 minutes in five-minute steps, so only the robot could ever produce the bad state. Deliberately **not** changed: the encoding that sends that third mode to the robot. No caller in the S7 Max Ultra's plugin produces it - but that is a statement about a different robot, and the Z70's own plugin is not available to us. Whether a third mode exists behind the firmware bit is named in the feature table, not proven, and how it travels is undecided in either direction; the table entry, the reader and the writer all arrived in one upstream commit, so they are one source rather than three. Removing it would be the irreversible direction, and it is already gated behind a bit that the reference robot does not report.
- (Eistee82) The cleaning order can be set from the tab, and the tab stopped guessing whether a map edit worked. Two things that met in the same file. **The order first.** The adapter learned to read it a while back and publish it; nobody could set one. It is now offered from the same room selection that combining uses - one selection, two uses, rather than a second way of picking rooms - and in the order the rooms were clicked, which is what the app sends too. The current order is shown **above** the buttons, and that is the point rather than decoration: `set_clean_sequence` replaces the whole order, so an interface that set one without displaying the existing one would overwrite something the user never saw. Clearing sends the empty array the app's own reset button sends, and the robot picks its own order again. The order is shown as room **names**; a segment id the current map no longer has is left out rather than printed as a bare number, because that is precisely the state a split leaves behind. And a state that cannot be read leaves the shown order alone instead of blanking it - empty is a real value here and means 'the robot decides'. **One honest limit is written at the code:** that the robot accepted an order is observable, that it cleans in that order is not - only a real segment run shows the difference, and nothing in the tab should be read as proof of the latter. **And the thirty-second wait is gone.** The tab used to watch for a zone edit to show up in the robot's published set and complain if nothing came within thirty seconds. That existed because *nothing at all* said anything when an edit failed: the socket answers ok as soon as the value is written, and every later refusal went to the adapter log. Since the adapter writes the outcome onto the command state itself - a quality and a reason on failure, both cleared on success - the tab reports the failure **immediately and with its reason**, instead of thirty seconds later saying only that nothing came. A success needs no message at all: the map redraws with the change. The old machinery and its tests went together; a stand-in that outlives the thing it stood in for is just another place to be wrong.

- (Eistee82) Three dock settings that only one model class ever had are now offered to every robot that proves it has them: how thoroughly the dock washes the mop, how often the robot returns to wash it, and whether carpets get a second pass after a room clean. Each is unlocked by asking the robot its own getter, never by its model name - the same rule the other probed settings follow, and the reason it exists is that one robot can answer `get_wash_towel_mode` and reject its immediate neighbour `get_wash_towel_params`. **What had kept them out was a note in the code that turned out to be wrong**, and it is corrected in place: it said all three setters hand their argument to the robot unread, so the payload could not be known. That is true of exactly one of them; the other two build their payload themselves and always did. What was really missing was not the shape but the **range of values**, and that is what has now been read out of the app rather than guessed. The wash mode is the case that punishes guessing: its values run 0, 1, 2, 8, 10, so counting one step past *Deep* would send a different command than the one intended. Only the three the app shows unconditionally are offered here; the other two hang on conditions the robot only reveals later, and offering a value on the chance that it applies is the dead switch this adapter keeps removing. The wash frequency is one setting rather than two, because the robot has one call for it and the app shows one row: either the dock decides by room, or an interval from 10 to 50 minutes. The interval is sent in seconds, which is proven in both directions - the app multiplies by 60 on the way out and divides by 60 on the way back. All three are read from the robot at start-up and read again after every write, because none of them appears in the status packet, so the robot is the only authority on what it really took. Every wording comes from Roborock's own strings, so nothing needed translating.
- (Eistee82) Rooms can be combined from the tab, and nothing is sent before the warning has been read. Combining renumbers the robot's segments, so everything that referred to a room by its old number then refers to a different one - and the numbers are invisible, so the damage shows up as the robot cleaning the wrong room rather than as an error. The adapter has warned about this from the start, in the log and in the description of the command state; neither reaches the person pressing a button, which made the tab the one place where the warning was missing and the action was easiest. **So the warning was built before the function.** Its first sentence is Roborock's own `map_edit_segment_prompt`, in all eleven languages the tab speaks - a rewrite would be a second, slightly different claim about the same firmware behaviour, and this is the sentence the user may already know from their phone. Under it stand the three concrete consequences, and the first one is the uncomfortable one: **room-bound suction and water settings live on the robot and the adapter does not have them at all**, so it cannot save them and cannot put them back. That is said plainly rather than hidden behind 'related settings', because a warning that implies a promise the adapter cannot keep is worse than none. The other two it can handle - the cleaning order is cleared automatically, the room switches are rebuilt - but whatever was hung on those switches in scripts, vis or scenes is the user's to re-point. The prominent button is Cancel: none of this can be undone from the tab, so the safe choice is the one the hand reaches for, and a stray Enter must not combine two rooms. Combining itself works off the room selection on the map, in the order the rooms were clicked, because that is what the user can see - and it is what the app sends too. Below two picked rooms the button is greyed out rather than hidden, since a button that only appears once the right number is picked is a button nobody finds. Whether the rooms actually touch stays the robot's decision: the adapter has no adjacency to test with, and a robot that says no leaves the map alone. **Dividing a room is not offered yet** - it needs a line drawn inside the room, which is a map gesture of its own rather than a button.

- (Eistee82) **A state told users their robot could not restore a map backup. It was answering the wrong question.** `mapInventory.restoreSupported` probed `get_recover_maps`, the reference robot answers `unknown_method`, and the state therefore said "no" — beside two backups it had just listed. **The probe asked about a different feature.** The app has **two** restore flows and they share no call at all: the older *Reset map* page lists through `get_recover_maps` and restores with `recover_map(id)`, while *Map backup* — the entry gated by `new_feature_info` **bit 49**, `isSupportBackupMap` — takes its list from the `bak_maps` the adapter already reads out of `get_multi_maps_list` and restores with `recover_multi_map`. So both earlier readings were right about their own flow: the old one really is absent on this robot, and the bit really does mean something. What was wrong was joining them. **The claim that the Roborock app would show an empty restore list on this robot is withdrawn**; it would show one entry per floor. The state now answers what its two proven halves can answer together — *there are backups, and this robot's menu offers them* — and it says so in its own description, because it is emphatically **not** a promise that restoring works. `recover_multi_map` is a write, it has never been measured, and it will not be: it overwrites the map that is loaded, and Roborock's own warning says the schedules and commands attached to it stop working. Proving a destructive call by making it is not a capability probe. **One deliberate asymmetry**: a *cleared* bit is the robot saying no and is reported as no, but a *missing* `new_feature_info` says nothing at all, and there the backup count decides alone — answering "no" to silence is the exact fault being repaired here. Two details are now written where the next person will need them rather than only in the analysis: `recover_multi_map` is handed the flag of the **live** map and not the backup's (0 or 1 here, while the backups call themselves 4 and 5), and the payload **never names the backup** — with one backup per map that is unambiguous, and whether a robot keeping several can be told which one is not answerable from the app package. The check also costs one request less than before, because the probe is gone and the bit rides along in a status the adapter already has.
- (Eistee82) **The water level "Extreme" was still there, because the field that removes it never arrived.** The gate that takes `water_box_mode = 208` away from robots without firmware bit 45 was correct and did nothing, and the reason is one line further back than the gate: it reads `new_feature_info_str` out of the status packet, and **the reference robot's `get_status` does not contain it**. 51 fields, measured twice 4 h 47 min apart, and neither bitfield among them. Both are answered by `app_get_init_status` and by nothing else — a call the adapter made nowhere at all. So the reader saw an absent field, took the conservative branch it was built with ("absent is not a denial, keep the level"), and the dead control stayed on screen. `app_get_init_status` is now asked once per run, before the first status packet, and its two bitfields are published as ordinary `deviceStatus` states. That closes the reported fault and **three more of the same kind**, because four places read those two states and every one of them was reading an absent state as "no": the map editor sent its payloads without the retry envelope although bit 26 is set and the envelope is mandatory when it is, the live map never used the incremental update although bit 22 is set, and the Matter name sync stayed off — correctly, as it turns out, that bit really is clear. **A robot that does not answer the call is left exactly as it was**; the one bit that removes a control may only do so on a positive answer, and silence is not one. Where a robot does carry the field in its status, the status still wins: it is the fresher of the two.
- (Eistee82) **An answer the adapter has no name for now becomes a state.** `requestAndProcess` wrote states only when a robot's answer unwrapped to a plain object. Anything else — a bare value, a list, an empty list — reached the end of the function and disappeared: no state, no log, no error. Measured against every answer the reference robot gives, **28 of 43 arrived and 15 were dropped**. A writable state whose range nobody knows is the exact fault this project has refused four times — `save_map` drops every zone not sent with it, `WashTowelModeMap` jumps 2 → 8 → 10, and the robot acknowledges an out-of-range value with `["ok"]` before discarding it. Arrays are also labelled `array` instead of `object` now, which is what ioBroker has the type for.
